# Architecture Decisions

- **D001 (proposed):** OpenCode stable v1 per-project agent files live in `.opencode/agents/`, not in plain `agents/`.
- **D002 (proposed):** Builder is primary; Reviewer is read-only subagent, invoked on demand.
- **D003 (proposed):** Reviewer returns a report in its response; Builder saves it to `reviews/` to preserve edit-denied review isolation.
- **D004 (proposed):** Contract first; no false-positive testing aligned to buggy implementation.
- **D005 (proposed):** No real external API is required for this first portfolio project.
- **D006 (adopted for AQL-000):** Run `.ts` sources directly with Node 24's built-in type stripping instead of adding `ts-node`/`tsx`; TypeScript stays a devDependency used only for `tsc --noEmit` typechecking.
  - Alternatives: `tsx` (fast but extra runtime dependency), `ts-node` (loader friction with ESM), or a `tsc` build step producing `dist/` (extra artifact to keep in sync).
  - Rationale: no build step or runtime transpiler to maintain; CI and local runs execute identical files. Verified on Node v24.19.0 — a probe file `.probe.ts` containing a typed declaration ran with `node .probe.ts` → exit 0, output `ts-strip-ok 42` (probe deleted afterwards).
  - Constraint: type stripping erases types only. `erasableSyntaxOnly` is enabled so typechecking rejects non-erasable syntax (`enum`, `namespace`, parameter properties, decorators); `verbatimModuleSyntax` is enabled separately so type-only imports are explicit rather than silently elided by the compiler.
- **D007 (adopted for AQL-000 review fix):** Validate `engines.node` with `semver` (`validRange` + `subset(range, ">=24.0.0")`) instead of a regex.
  - Alternatives: narrow hand-written format parser (simpler, but easy to under-approximate and hard to explain); regex over the raw string (rejected — a substring such as `>=24` passes inside `garbage >=24` and inside `>=24.0.0 || >=18.0.0`).
  - Rationale: `subset` answers the actual question — does this range permit any version below the project minimum? — and rejects malformed input via `validRange === null`. Reviewer regression cases are pinned in `harness/doctor.selftest.ts`.
- **D008 (adopted for AQL-100):** Errors use RFC 9457 `application/problem+json` with a stable `code` and optional `errors[]` field list.
  - Alternatives: bare `{message}` (no machine-readable discriminator, weak assertions); custom `{error:{...}}` envelope (invents a format and loses standard tooling); plain-text errors (untestable structure).
  - Rationale: `code` gives tests a stable contract target independent of human wording, `errors[]` supports per-field validation assertions, and RFC 9457 is a documented standard. `Problem.additionalProperties: false` also makes stack-trace leakage a contract violation that tests can detect. Error codes are listed in `x-error-codes` with their fixed status.
- **D009 (adopted for AQL-100):** Cross-user access to another user's item returns 404 `item_not_found`, not 403.
  - Alternatives: 403 Forbidden (reveals that the id exists and belongs to someone else, enabling enumeration); 401 (wrong semantics — the caller is authenticated).
  - Rationale: 404 keeps foreign-owned and nonexistent ids indistinguishable, so a mutation that skips the ownership check is detectable only by the status/body difference, not by an information leak. Tests assert the same code for both cases (REQ-ISO-01, REQ-ITEM-08).
- **D010 (adopted for AQL-100):** Requirement IDs and error codes live inside `openapi.yaml` as `x-requirements` (including an `appliesTo` applicability matrix), `x-error-codes`, operation `x-requirement-ids` and response `x-error-codes`, and are verified by a fail-closed `contract:validate` plus a 56-case `contract:selftest`.
  - Alternatives: separate `requirements.md` table (duplicates the source of truth and invites drift; markdown parsing is brittle); relying on schema validation alone (a syntactically valid contract can still drop auth, weaken a bound or register an unused code); operation links without `appliesTo` (requirement coverage is "referenced somewhere", not "attached to every applicable operation").
  - Rationale: one artifact holds behavior and traceability; the validator enforces exact bidirectional consistency between the declared applicability matrix and operation links, the exact operation set, auth coverage, required request/error/success shapes, header references at each applicable response, problem envelopes, schema strictness and G1 boundaries. Effective component schemas plus POST /items operation-level schemas are compiled with AJV 2020-12 and probed with 63 valid/invalid instances (PATCH max-price and field-type probes included), so the tested keyword-level contradictions (extra `exclusiveMinimum`/`allOf`/`not`, widened `type`, impossible conditional) are detected; the instances establish their tested cases, not universal protection against every possible schema contradiction.
  - Verification guarantee: every reject case asserts the exact check id that must fail; cases targeting a specific subrule also assert a diagnostic substring. Remaining cases guarantee check-level attribution, not full causal isolation within an aggregated check.
  - History: review round 1 found six weakening mutations and two rule gaps; round 2 found type/boundary, header/media/conditional and malformed-`appliesTo` gaps; round 3 found operation-level header-reference and `$ref`-sibling/instance gaps. All are now covered by regression controls; each round's report is preserved in `reviews/AQL-100.md`.
- **D011 (adopted for AQL-100):** Two synthetic users (`alice`, `bob`) with opaque bearer tokens; default local server `http://127.0.0.1:3000`, overridable through `AQL_BASE_URL`.
  - Alternatives: JWT with claims (adds signing/key handling with no QA benefit); random users per run (breaks the fixed synthetic-user requirement); hard-coded single port (collides with other local services).
  - Rationale: opaque tokens keep the SUT intentionally simple while still exercising missing/invalid/valid token paths; two fixed users make cross-user isolation and fixture reset deterministic. Port 3000 is a documented default, not a constraint on the test runner.

- **D012 (adopted for AQL-200):** Synthetic credentials are `alice` / `alice-password` (`usr_alice`) and `bob` / `bob-password` (`usr_bob`), documented in `sut/README.md`; the SUT is a dependency-free Node `http` server with per-instance in-memory state.
  - Alternatives: hashed/secret-managed credentials (no benefit for local synthetic users; hides the fixture); a web framework such as Express/Fastify (extra dependency for seven operations); persistent file/database storage (state leaks between runs, breaks deterministic isolation).
  - Rationale: the contract names the users but not their passwords, so the passwords are fixed synthetic fixtures recorded here and in `sut/README.md`. Plaintext comparison is acceptable only because these are local synthetic accounts. In-memory state makes fixture reset deterministic: a fresh server instance or `reset()` starts empty, and start/stop is the isolation boundary the QA suite controls.
  - Token expiry: `expiresIn` is 3600 seconds and is enforced against issuance time. Enforcement is implemented in `authenticate()` and exercised by a deterministic fake-clock unit test (`InventoryServerOptions.now`/`tokenTtlSeconds`), not by waiting in tests.

- **D013 (adopted for AQL-200, user instruction):** Every update that is committed and pushed also updates the GitHub `README.md` in the same commit, so the public status always matches the pushed code.
  - Alternatives: README updated in a later docs-only commit (public page can describe code that is not there yet, or lag behind it); a generated status badge fed by CI (no CI exists until AQL-500, and a badge cannot carry the honest "not verified" nuance this project requires).
  - Rationale: this is a portfolio repository; a stale README is a false claim about the work. The status table distinguishes DONE / REVIEW_REQUIRED / TODO / NOT VERIFIED per gate instead of a single optimistic summary.

- **D014 (adopted for AQL-300):** Playwright API tests use a per-test in-process SUT instance on an ephemeral loopback port, with a fresh `APIRequestContext` per test, instead of Playwright's shared `webServer` or an out-of-contract reset endpoint.
  - Alternatives: one shared `webServer` for the whole suite (fast, but items/tokens leak between tests and make order dependence possible); a test-only `POST /reset` endpoint (adds behavior outside the contract and weakens the "no reset endpoint" design); restarting a child `sut/src/server.ts` per test (more realistic process boundary, but slower and duplicates AQL-200's start/stop coverage).
  - Rationale: `createInventoryServer()` exposes `reset()` only to in-process callers, and a fresh instance gives every test an empty item/token store without changing the contract. The fixture still exercises a real HTTP listener through Playwright's `APIRequestContext`. Because no test can observe another test's state, order independence is structural, not just a passing coincidence.
  - Verification: 32 tests pass twice consecutively with one worker, and the same suite passes with `--shuffle=20261101 --workers=4 --fully-parallel`; evidence is recorded under `evidence/generated/aql-300-qa-*`. The process-level start/stop claim remains AQL-200's, not AQL-300's.

- **D015 (adopted for AQL-300 review fixes):** The SUT's existing injectable `now` clock also governs item `createdAt`/`updatedAt`, and the Playwright fixture exposes `setNow(ms)` so the ordering test can create a deterministic timestamp tie.
  - Alternatives: relying on wall-clock bursts until two creates share a millisecond (nondeterministic and potentially vacuous); monkey-patching the global `Date` in the test process (affects Playwright internals and is hard to scope); adding a test-only seed endpoint (behavior outside the contract).
  - Rationale: `createInventoryServer({ now })` already existed for deterministic token-expiry tests. Extending it to item timestamps is a testability hook with unchanged default behavior (`Date.now`) and no contract change. The QA test proves a three-item tie before asserting ascending-id order, so REQ-ITEM-04's tie-break is exercised rather than conditionally skipped.
  - Verification: QA-LIST-02 passes with a fixed clock; `npm run test:unit` remains green.

- **D016 (adopted for AQL-300 review fix):** Traceability uses Playwright's own `--list --reporter=json` discovery instead of scanning spec source with a regex.
  - Alternatives: keeping the source regex and adding an allowlist (still counts commented/nonexecutable strings); parsing the human `--list` text output (brittle formatting); importing spec modules directly (executes collection outside Playwright's runner).
  - Rationale: discovery is the same set of tests Playwright will run, so commented strings and unregistered helpers cannot satisfy coverage. The check still fails closed on missing/duplicate/unknown ids, matrix drift and uncovered requirements. `qa:traceability:selftest` adds negative controls for the parser and reconciliation.
  - Verification: `npm run qa:traceability` reports 32 executable tests and 28/28 requirements; `npm run qa:traceability:selftest` reports all negative controls passing.

- **D017 (adopted for AQL-400):** Mutation evaluation patches `sut/src/app.ts` in place with exact single-occurrence replacements, runs the targeted Playwright spec, and restores the original bytes in a `finally` block with SHA-256 verification; the full 32-test suite runs before and after all mutations.
  - Alternatives: copying the repository (or SUT plus `qa/`) to a temporary directory (heavier, and `qa/fixtures/inventory.ts` imports the real SUT path; a copy would need its own `node_modules` or symlinks); keeping mutation switches in production SUT code behind an environment variable (ships test-only branches in the SUT and weakens the "mutation" claim); running the full suite per mutation (slower without adding detection value because each mutation is scoped to a known requirement area).
  - Rationale: in-place patching exercises exactly the code the API tests import, and the hash check makes restoration an observed fact rather than an assumption. `applyMutation` fails closed on missing, ambiguous or no-op anchors. Each mutation's run must produce exit code 1, exactly the expected failing QA ids, the exact assertion signature, and the exact Playwright `Expected:`/`Received:` pair (QA-VAL-02 `400`/`201`, QA-VAL-07 `>= 3`/`2`, QA-AUTHZ-02 `401`/`200`, QA-ISO-01 `404`/`200`); missing or ambiguous values, HTTP 500 and wrong received values fail closed, as do setup/crash markers; the post-restore full suite must pass 32/32. The auth test asserts status `401` before the challenge header so a wrong `500` is distinguishable. SIGINT/SIGTERM handlers restore on interruption; a hard `SIGKILL` cannot be intercepted, so the recorded baseline hash (`shasum -a 256 sut/src/app.ts`) is the recovery check. The file already carries legitimate uncommitted AQL-300 changes, so `git diff` is not a clean-tree check.
  - Verification: `npm run harness:eval` detects all three mutations with their exact expected/received semantics, restores the SUT hash, and re-passes 32/32; `npm run harness:eval:selftest` passes 37 negative/positive controls, including HTTP-500 and wrong-received negatives for every expected QA id. Tests and contract are never edited.

- **D018 (adopted for AQL-500):** CI is a single sequential GitHub Actions job with HTML/JUnit reports per run, separated baseline/mutation report directories, a fail-closed report verifier, and a pre/post SUT hash check.
  - Alternatives: parallel jobs for unit/API/harness (faster, but `harness:eval` patches `sut/src/app.ts` in place, so any overlapping job could import mutated code); one aggregate report directory (a green baseline could be confused with intentional mutation failures); trusting Playwright's report files without checking them (a missing or malformed report would still upload "successfully"); relying on `git diff --exit-code -- sut/src/app.ts` for restoration (correct in a clean CI checkout, but a false failure in this worktree, which legitimately carries uncommitted AQL-300 changes).
  - Rationale: one job makes the mutation window exclusive by construction; `concurrency.cancel-in-progress: false` avoids cancelling a run mid-restore. Playwright emits `json,html,junit` together, with JSON on stdout so the existing `harness:eval` parser and exit semantics are unchanged. Reports go to `api-baseline`, `harness-eval/baseline-pre`, `harness-eval/baseline-post` and `harness-eval/mutations/<id>`; the workflow uploads them as separate artifacts. `harness/report-check.ts` parses JUnit counts/failures/errors/skipped, checks declared counts against elements, requires the exact QA testcase inventory for baselines (32 ids) and mutation specs (9/2/2) with the exact failing subset and no missing/extra/duplicated/substituted ids, and requires Playwright-specific HTML markers (report title plus embedded report data); its 14-case self-test adds generic-HTML, unrelated-baseline, substituted-id, duplicated-id, non-QA-name and wrong-mutation-inventory negatives to the missing/malformed/wrong-count/wrong-failure/missing-HTML controls. These are consistency/authenticity sanity checks, not cryptographic provenance. The workflow records `sha256sum sut/src/app.ts` before evaluation and compares it after, restoring from git and failing on mismatch.
  - Scope limit: report verification is structural, not a full XML-schema validator; the baseline is pinned to 32 tests and the three mutation expectations, so a deliberate suite change requires updating those constants.
  - Verification: `evidence/generated/aql-500-ci-20261101T0345Z/` — API baseline JUnit 32/0; harness baselines 32/0 twice; mutation JUnit 9/2, 2/1, 2/1 with the intended QA ids; `reports:verify` PASS; `reports:selftest` 8/8; `harness:eval` 3/3 with the SUT restored to `c2f33ba4…d2d7fd`; `actionlint` 1.7.12 exit 0. **Remote GitHub Actions has not run, so G5 remote is NOT VERIFIED.**

Record material deviations with alternatives, rationale and evidence.
