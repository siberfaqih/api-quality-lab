## Findings

### R1 — MEDIUM: Valid Unicode strings rejected

**Location:** `sut/src/app.ts:97,125,185`

**Impact:** String limits count UTF-16 code units rather than JSON Schema characters. Valid names and descriptions containing supplementary Unicode characters are rejected, violating REQ-VAL-01/04. Login length validation has the same implementation issue.

**Evidence:**
- Create with `name: "😀".repeat(80)`, `price: 1`, `quantity: 1` returned **400**, `name/too_long`.
- Create with `description: "😀".repeat(500)` returned **400**, `description/too_long`.
- Independently compiling the contract’s `ItemCreateRequest` with AJV accepted a payload containing both strings.

**Remediation:** Count Unicode code points consistently with JSON Schema. Add create/PATCH tests at and beyond these boundaries, including supplementary characters.

### R2 — MEDIUM: Decimal tolerance accepts forbidden prices

**Location:** `sut/src/app.ts:88–90,102–109`

**Impact:** Over-precision prices are accepted and stored, violating REQ-VAL-02 and the Item response constraints.

**Evidence:** Authenticated creation with:

```json
{"name":"precision","price":0.000000000001,"quantity":1}
```

returned **201**, including `"price":1e-12` in the created item. The fixed `1e-9` tolerance treats sufficiently small fractional-cent values as valid.

**Remediation:** Implement decimal validation that accommodates binary representation of valid cent amounts without accepting genuine fractional cents. Add create/PATCH regressions for tiny positive values and near-cent values; verify rejected requests leave state unchanged.

### R3 — MEDIUM: Large offset produces a schema-invalid successful response

**Location:** `sut/src/app.ts:358–381`

**Impact:** A digit-only offset overflowing JavaScript’s number range is accepted as `Infinity`, then serialized as `null`. The **200** response violates `ItemList.offset: integer`.

**Evidence:**

```text
GET /items?offset=<400 repetitions of 9>
```

returned:

```json
{"items":[],"total":1,"limit":20,"offset":null}
```

An independent AJV check rejected this response shape.

**Remediation:** Handle numeric conversion overflow explicitly. Never emit a successful response with a non-integer/null offset. Document any representability policy and add overflow/large-integer query tests without silently imposing an arbitrary contract maximum.

### R4 — MEDIUM: Empty unknown property produces invalid FieldError

**Location:** `sut/src/app.ts:164–166,191–193`

**Impact:** Unknown-property rejection can itself violate the mandatory Problem schema, contrary to REQ-ERR-01.

**Evidence:** Creating with:

```json
{"name":"ok","price":1,"quantity":1,"":true}
```

returned **400** with:

```json
{"field":"","code":"unknown_property","message":" is not a supported property"}
```

`FieldError.field` requires `minLength: 1`. Independent AJV validation rejected this entry. Login uses the same raw-key reporting pattern.

**Remediation:** Represent empty property names with an unambiguous, non-empty request path. Add login/create/PATCH regressions validating the complete Problem and FieldError schemas.

### R5 — LOW: Several tests do not prove their stated guarantees

**Location:** `sut/app.test.ts:189–205,256–261,302,503–509`

**Impact:** Some regressions can escape despite requirement-labelled passing tests.

**Evidence from source inspection:**
- “advances updatedAt” uses `>=`, accepting an unchanged timestamp.
- Pagination checks slice length but not the exact expected item.
- The reset test proves token invalidation, not item clearing after re-login.
- Missing-token tests cover GET operations only; invalid-token tests cover list only, although the requirements apply to all five protected operations.

These are assertion gaps, not evidence that the current implementation fails those behaviors. My independent probes verified strict timestamp advancement, reset clearing and broader authentication handling.

**Remediation:** Strengthen these assertions and add deterministic expiry/fresh-instance checks. Validate complete response shapes rather than relying solely on TypeScript casts.

### R6 — LOW: Documentation contains stale or unsupported present-tense claims

**Location:** `PROGRESS.md:142`; `sut/README.md:34`; `DECISIONS.md:33`

**Impact:** Readers can confuse historical status or implementation intent with executed evidence.

**Evidence:**
- The historical-audit update says G2 “remain[s] BLOCKED / NOT VERIFIED,” conflicting with the later current G2 section.
- SUT documentation says restart is the isolation boundary the “QA suite uses,” while AQL-300 has not been implemented.
- D012 says expiry is “exercised by state design”; the submitted unit suite contains no expiry exercise. Enforcement exists in code, and my simulated-clock probe independently verified it.

**Remediation:** Clarify historical scope, use future tense for AQL-300, and distinguish implemented expiry enforcement from automated test evidence.
